# Computer groups

On each computer, open **Remote workspace → Computer group** or **Settings → Mobile → Computer group settings**. If the listener is off, choose **Enable computer group connections**; this does not enable phone or one-to-one sharing. Create the group on the first computer. An existing member can copy a short-lived, one-time invite for a new computer. The joiner reviews the scope and submits the request; both computers compare the code, and the inviting member explicitly approves it. A group does not import or upgrade previous pairings.

This is full trust within BaoCode, not read-only access. Members can operate agents, answer approvals, read files BaoCode can access outside projects, and approve or remove members. Selected computers use the existing Iroh transport, including its configured relay fallback; the inviter is not a hub. Pause the group on a computer to disconnect its group sessions without forgetting memberships or changing legacy access.

Removal denies and disconnects group workspace access on this computer once it knows the signed removal. The app exchanges changes while it is running and on group connections, with a manual **Sync membership changes** button. Pending acknowledgments can mean a computer is offline or otherwise unreachable; unchanged membership is not a live presence indicator. Confirmation is based on the authenticated peer reporting the exact signed event after storage readback; those observations are not persisted and refresh on the next sync after restart. An offline computer can still be unaware of the removal. Existing one-to-one access, if separately granted, is unaffected.

## Implementation notes

- `LinkHost` owns group membership; the v1 `computer-group.json` file is separate from `mobile.json` and the legacy desktop client store. Each desktop uses its same Ed25519/Iroh listener identity for incoming and outgoing group traffic. Legacy outgoing pairings still use their separate keys. Both the local Iroh node ID and the remote authenticated endpoint ID are checked before group RPCs are sent.
- `computerGroup.prepare` returns the pinned, verified history to the invite holder. The joining identity then signs the exact group, sponsor, nonce, identity and route with the full workspace/delegation scope. An admission event contains that consent and is signed by the approved sponsor. A plain group connection never becomes a legacy pairing. `computerGroup.sync` exchanges signed evidence; `computerGroup.open` is a separate step that requires an eligible authenticated member. The normal `WorkspaceBridge` serves that workspace, and the desktop workspace model retains one selected outbound workspace.
- The signed membership DAG authorizes changes against their causal history. A removal wins over stale grants for the same identity and admissions by a removed sponsor not seen by the removal. Known admissions that preceded removal of their sponsor survive. There is no central membership authority or guaranteed global order during a partition.
- This slice supports one group per installation; there is no group reset, rejoin with a revoked identity, or key rotation UI. Saved group routes are signed at admission and supplemented by already discovered LAN addresses when opening a workspace. A direct-only peer that changed addresses and is not discoverable may be unreachable; a common configured relay avoids dependence on stored LAN hints. Storage errors disable group access in the running app and are reported; if the storage itself loses or rolls back a previously valid snapshot, it cannot prove a later event without syncing again.
